# UpdatePulse Server agent instructions

These instructions apply to every change under `wp-content/plugins/updatepulse-server/`. They supersede the repository-level plugin skeleton where this plugin's established architecture differs from that skeleton.

## Scope and branch

- Work only in this plugin.
- Preserve unrelated user changes. Inspect `git status --short` before and after editing.
- Do not edit bundled libraries under `lib/` merely to make application code convenient. Treat them as vendored code. An exception is an explicit update to this plugin's maintained Package Update Checker fork or an explicit VCS-provider implementation; in that case, keep the library API backward compatible with all existing providers.
- Do not edit this file unless the user explicitly asks.

## Before changing code

Read the complete implementation path involved in the change, not just the named file. At minimum:

1. Read `updatepulse-server.php`, `autoload.php`, and the constructor of every participating class.
2. Trace the request context. Update, license, package, webhook, cron, AJAX, CLI, and ordinary admin requests deliberately load different objects.
3. Trace stored data through `upserv_get_option()`, `upserv_set_option()`, `upserv_update_options()`, package metadata, custom tables, and upload directories as applicable.
4. Trace every related action and filter. This plugin exposes a large public extension surface documented in `docs/`.
5. Read the manager/API method, template, unminified JavaScript, unminified CSS, and relevant documentation together for UI changes.
6. For VCS work, read `Remote_Sources_Manager`, `Update_Server::build_update_checker()`, `Update_Server::init_update_checker()`, webhook candidate selection, the Package Update Checker VCS base class, and every existing provider implementation.
7. Search for the affected option key, hook, endpoint, class, string, and public function across PHP, JavaScript, templates, `README.md`, `readme.txt`, `docs/`, and `languages/updatepulse-server.pot`.

Do not use an existing defect or inconsistency as a pattern. Preserve public compatibility when necessary, but write new code to the standards in this file.

## Architecture

### Bootstrap and request-aware loading

`updatepulse-server.php` is the bootstrap and performance boundary:

1. It defines `UPSERV_PLUGIN_PATH`, `UPSERV_PLUGIN_FILE`, `UPSERV_PLUGIN_URL`, and byte-conversion constants.
2. It loads `autoload.php` through the `upserv_mu_require` filter.
3. It initializes `Nonce` authentication before normal plugin startup.
4. It registers lifecycle callbacks for participating classes.
5. It registers the `updatepulse-server` WP-CLI command when `WP_CLI` is active.
6. `upserv_run()` constructs only the objects required by the current request and fires `upserv_ready` with the resulting object map.
7. `upserv_updater()` loads the bundled migration runner outside API requests.

Request detection is part of correctness and performance. The normal object graph is:

- Always: `Scheduler`, `License_API`, and `Webhook_API`.
- Outside the priority license-API path: `Update_API`, `Package_API`, and `Cloud_Storage_Manager`, plus required WordPress admin includes.
- Outside all API paths: `Data_Manager`, `Remote_Sources_Manager`, `Package_Manager`, `License_Manager`, `API_Manager`, and `UPServ`.

`upserv_objects` allows a prebuilt object to replace a default object by key. `upserv_no_priority_api_includes` and `upserv_no_api_includes` allow integrations to load additional dependencies at the corresponding boundaries. `upserv_is_priority_api_request` and `upserv_is_api_request` classify requests. Changes to those filters can affect which managers exist; trace every request type before changing them.

Do not put feature logic in the bootstrap. New internal components belong in focused namespaced classes and are constructed in `upserv_run()` only in the contexts where they are needed. Keep constructors cheap: initialize properties and register hooks only when `$init_hooks` is true. Do not perform writes, remote requests, redirects, or expensive scans in constructors.

An internal component follows this shape:

```php
namespace Anyape\UpdatePulse\Server\Manager;

class Audit_Manager {
	public function __construct( $init_hooks = false ) {
		if ( ! $init_hooks ) {
			return;
		}

		add_action( 'upserv_did_download_package', array( $this, 'record_download' ), 10, 1 );
		add_filter( 'upserv_admin_tab_links', array( $this, 'add_tab_link' ), 25, 1 );
	}
}
```

Then import and instantiate it in the correct `upserv_run()` branch, respecting an injected object:

```php
if ( ! isset( $objects['audit_manager'] ) ) {
	$objects['audit_manager'] = new Audit_Manager( true );
}
```

If the class owns activation, deactivation, or uninstall work, add it to `upserv_mu_plugin_registration_classes` and implement only the methods it needs. Verify the exact callable; lifecycle registration must not silently reference a misspelled class or method.

### Autoloading and file layout

Plugin classes use the `Anyape\UpdatePulse\Server` namespace. `autoload.php` maps namespace fragments and underscore-separated class names to lowercase kebab-case files under `inc/`:

```text
Anyape\UpdatePulse\Server\Manager\Audit_Manager
-> inc/manager/class-audit-manager.php

Anyape\UpdatePulse\Server\API\Report_API
-> inc/api/class-report-api.php
```

Use one primary class per class file. Add a class-map entry only for a class outside that convention. Shared global functions belong in `functions.php`, must begin with `upserv_`, and must be guarded with `function_exists()`. Do not introduce a generic global or a second autoloader for plugin classes.

Relevant ownership is:

- `inc/class-upserv.php`: common options, shared admin shell, tabs, template location, common admin assets, activation requirements, and translations.
- `inc/manager/`: focused workflows and admin screens. Package, license, remote-source, API settings, data-directory, cloud-storage, and ZIP concerns remain separate.
- `inc/api/`: rewrite registration, query variables, authentication/authorization, request dispatch, response shape, and API event hooks.
- `inc/server/update/`: update request parsing, package discovery, VCS update checks, downloads, caching, licensing gates, and responses.
- `inc/server/license/`: license persistence and domain/state rules.
- `inc/table/`: `WP_List_Table` presentation, sorting, pagination, row actions, and bulk actions.
- `inc/scheduler/`: the Action Scheduler/WordPress Cron compatibility facade.
- `inc/nonce/`: token/nonce API, signature authorization, persistence, and cleanup.
- `inc/cli/`: thin WP-CLI adapters over public functions and APIs.
- `inc/templates/`: presentation only.
- `functions.php`: stable public procedural API delegating to managers/APIs.
- `optimisation/`: the MU-plugin request optimizer copied into `WPMU_PLUGIN_DIR` on activation.
- `updates/`: versioned migrations loaded by `WP_Update_Migrate`.

### Data and lifecycle

The primary settings record is `upserv_options`, stored as pretty-printed JSON. Defaults are declared in `UPServ::$default_options`. Nested paths use slash notation such as `api/packages/private_api_keys`, `limits/cache_max_size`, or `cloud_storage/region`.

When adding an option:

1. Add a backward-compatible default to `UPServ::$default_options`.
2. Read it through `upserv_get_option( $path, $default )`.
3. Add a sanitized submission definition to the manager that owns the screen.
4. Validate the sanitized value before adding it to the save map.
5. Use `upserv_set_option()` to update the in-memory nested array and call `upserv_update_options()` once for the completed update.
6. Never log or expose secret values. Preserve existing credentials when a form intentionally omits or masks them.
7. Add a migration under `updates/` when existing stored data must be transformed. Do not perform a schema/data migration on every request.

Persistent data also includes:

- `{$wpdb->prefix}upserv_licenses`, owned by `License_Manager`/`License_Server`.
- `{$wpdb->prefix}upserv_nonce`, owned by `Nonce`.
- `wp-content/uploads/updatepulse-server/packages/` and `metadata/`, which are persistent package data.
- `cache/`, `logs/`, and `tmp/`, which are transient and cleaned through `Data_Manager`.
- `upserv_update_from_remote_locks`, which is transient database state.
- scheduled `upserv_*` actions, with Action Scheduler used when available and WordPress Cron as the fallback.
- the copied `upserv-default-optimizer.php` MU plugin.

Use `Data_Manager::get_data_dir()` rather than constructing upload paths. Register a new directory in the appropriate persistent/transient list before requesting it. Protect plugin-owned directories consistently. Any new persistent record needs deliberate activation, migration, deactivation, and uninstall behavior. Never broaden uninstall cleanup beyond data owned by this plugin.

Use `Scheduler::get_instance()` instead of calling `as_*` or `wp_schedule_*` directly. Register callbacks when `upserv_scheduler_init` fires, guard against duplicates with `has_scheduled_action()`, and unschedule the same hook and arguments during disablement/deactivation.

## Adding an admin screen

Each screen is owned by a focused manager. Current screens are Packages Overview (`Package_Manager`), Version Control Systems (`Remote_Sources_Manager`), Licenses (`License_Manager`), API & Webhooks (`API_Manager`), and Help (`UPServ`). Cloud storage extends the Packages screen through package-option hooks instead of creating a competing screen.

A new screen requires all of the following:

1. A manager class loaded in the non-API branch of `upserv_run()`.
2. `admin_menu`, `upserv_admin_tab_links`, and `upserv_admin_tab_states` hooks in that manager.
3. A unique `upserv-page-*` slug, `manage_options` unless the feature defines and consistently enforces a narrower capability, and a page callback that repeats the capability check.
4. A template under `inc/templates/admin/` loaded with `upserv_get_admin_template()`.
5. A page-scoped settings handler that verifies `upserv_plugin_options_handler_nonce`, sanitizes, validates, saves, and places a success string or keyed error array in the `settings_notice` cache group.
6. Page-scoped scripts and styles registered through the shared filters.
7. Screen options and a `WP_List_Table` subclass when the page is tabular.
8. Help/user documentation, developer documentation for public contracts, translations, and validation.

Reference pattern:

```php
public function __construct( $init_hooks = false ) {
	if ( ! $init_hooks ) {
		return;
	}

	add_action( 'admin_menu', array( $this, 'admin_menu' ), 25 );
	add_filter( 'upserv_admin_tab_links', array( $this, 'add_tab_link' ), 25 );
	add_filter( 'upserv_admin_tab_states', array( $this, 'add_tab_state' ), 25, 2 );
	add_filter( 'upserv_admin_scripts', array( $this, 'add_admin_scripts' ) );
	add_filter( 'upserv_admin_styles', array( $this, 'add_admin_styles' ) );
}

public function admin_menu() {
	add_submenu_page(
		'upserv-page',
		__( 'UpdatePulse Server - Audit', 'updatepulse-server' ),
		__( 'Audit', 'updatepulse-server' ),
		'manage_options',
		'upserv-page-audit',
		array( $this, 'plugin_page' )
	);
}

public function add_tab_link( $links ) {
	$links['audit'] = array(
		admin_url( 'admin.php?page=upserv-page-audit' ),
		'<i class="fa-solid fa-list-check"></i>' . __( 'Audit', 'updatepulse-server' ),
	);

	return $links;
}

public function add_tab_state( $states, $page ) {
	$states['audit'] = 'upserv-page-audit' === $page;
	return $states;
}
```

The page callback prepares data; the template renders it:

```php
public function plugin_page() {
	if ( ! current_user_can( 'manage_options' ) ) {
		wp_die( esc_html__( 'You are not allowed to access this page.', 'updatepulse-server' ) );
	}

	wp_cache_set( 'settings_notice', $this->plugin_options_handler(), 'updatepulse-server' );

	upserv_get_admin_template(
		'plugin-audit-page.php',
		array(
			'entries' => $this->get_entries(),
			'options' => array(
				'enabled' => upserv_get_option( 'audit/enabled', false ),
			),
		)
	);
}
```

Templates must start with a direct-access guard, use the variables supplied by the caller, escape at output time, and keep queries, writes, redirects, authorization, hook registration, and business rules in the owning class. Use `esc_html()`, `esc_attr()`, and `esc_url()` by default; use `wp_kses_post()` only for deliberately allowed markup such as the shared settings header or icon-bearing tab labels.

To add a section to an existing page, prefer its explicit template action/filter. For example, the cloud-storage manager supplies package settings through `upserv_template_package_manager_option_before_miscellaneous` and extends submission through `upserv_submitted_package_config` and `upserv_package_option_update`. Do not duplicate the page's form processing in another class.

## JavaScript and CSS

Admin assets are registered, not directly printed. `UPServ::admin_enqueue_scripts()` invokes the shared registries only on UpdatePulse pages. Focused managers add definitions through `upserv_admin_scripts` and `upserv_admin_styles`.

Register page-specific assets conditionally:

```php
public function add_admin_scripts( $scripts ) {
	$page = isset( $_REQUEST['page'] )
		? sanitize_key( wp_unslash( $_REQUEST['page'] ) )
		: '';

	if ( 'upserv-page-audit' !== $page ) {
		return $scripts;
	}

	$scripts['audit'] = array(
		'path'   => UPSERV_PLUGIN_PATH . 'js/admin/audit' . upserv_assets_suffix() . '.js',
		'uri'    => UPSERV_PLUGIN_URL . 'js/admin/audit' . upserv_assets_suffix() . '.js',
		'deps'   => array( 'jquery' ),
		'params' => array(
			'ajax_url' => admin_url( 'admin-ajax.php' ),
			'debug'    => defined( 'WP_DEBUG' ) && WP_DEBUG,
		),
		'l10n'   => apply_filters(
			'upserv_scripts_l10n',
			array( 'confirmClear' => __( 'Clear the audit log?', 'updatepulse-server' ) ),
			'audit'
		),
	);

	return $scripts;
}

public function add_admin_styles( $styles ) {
	$page = isset( $_REQUEST['page'] )
		? sanitize_key( wp_unslash( $_REQUEST['page'] ) )
		: '';

	if ( 'upserv-page-audit' === $page ) {
		$styles['audit'] = array(
			'path' => UPSERV_PLUGIN_PATH . 'css/admin/audit' . upserv_assets_suffix() . '.css',
			'uri'  => UPSERV_PLUGIN_URL . 'css/admin/audit' . upserv_assets_suffix() . '.css',
			'deps' => array(),
		);
	}

	return $styles;
}
```

This produces the handle `upserv-audit-admin-script`, runtime variable `UPServAdminAudit`, and localization variable `UPServAdminAudit_l10n`. Runtime data such as URLs, nonces, IDs, booleans, and limits belongs in `params` and is emitted with `wp_add_inline_script()`. Only translated strings belong in `l10n`/`wp_localize_script()`. Declare expected globals at the top of the source JavaScript file.

Asset rules:

- Put editable sources in `js/admin/*.js` and `css/admin/*.css`.
- Keep a matching `.min.js` or `.min.css` file behaviorally equivalent to every source file. `upserv_assets_suffix()` selects sources when `WP_DEBUG` is true and minified files otherwise.
- This repository does not contain a committed JS/CSS build configuration. Use a deterministic, standards-compatible minifier available in the environment, record the command used in the handoff, and inspect the generated diff. Never hand-edit only the minified file.
- Use lowercase kebab-case filenames and asset keys. Existing underscore keys are compatibility artifacts; use kebab-case for new keys.
- Scope selectors beneath `.upserv-wrap` or another `upserv-` component root. Use `upserv-` for IDs and classes owned by the plugin; do not add generic `.item`, `.active`, `.hidden`, or element rules without a plugin-owned ancestor.
- Reuse the modal behavior in `js/admin/main.js` and `.upserv-modal*` styles when the interaction is truly a modal.
- Keep JavaScript page-scoped, event-driven, and compatible with the declared dependencies. AJAX actions use the `upserv_` prefix and return `wp_send_json_success()` or `wp_send_json_error()`.
- Check both the source and minified files. Empty, stale, or syntactically invalid minified files are release blockers.

## AJAX and form handling

State-changing admin requests require both a capability check and a nonce. A nonce is not authorization. Read, unslash, sanitize, then validate; do not apply a generic sanitizer to an entire nested structure when fields have different types.

```php
public function clear_audit() {
	if ( ! current_user_can( 'manage_options' ) ) {
		wp_send_json_error( new WP_Error( 'upserv_forbidden', __( 'Forbidden.', 'updatepulse-server' ) ), 403 );
	}

	$nonce = sanitize_text_field( wp_unslash( filter_input( INPUT_POST, 'nonce' ) ) );

	if ( ! wp_verify_nonce( $nonce, 'upserv_plugin_options' ) ) {
		wp_send_json_error( new WP_Error( 'upserv_invalid_nonce', __( 'Invalid request.', 'updatepulse-server' ) ), 403 );
	}

	$result = $this->delete_entries();
	$result ? wp_send_json_success() : wp_send_json_error( new WP_Error( 'upserv_clear_failed', __( 'Unable to clear entries.', 'updatepulse-server' ) ) );
}
```

For forms, distinguish absence from an invalid value. Booleans may validly be false and integers may validly be zero. Validate enum values against an explicit allowlist. Validate URLs with the appropriate WordPress/PHP URL API. Validate paths and slugs before filesystem access. Use prepared SQL and allowlist dynamic column/order names because placeholders cannot protect identifiers.

## APIs and request endpoints

This plugin uses WordPress rewrite rules and `parse_request`, not the REST API. Current public paths are:

- `/updatepulse-server-update-api/`
- `/updatepulse-server-package-api/` and `/updatepulse-server-package-api/{plugin|theme|generic}/{slug}/`
- `/updatepulse-server-license-api/`
- `/updatepulse-server-webhook/` and `/updatepulse-server-webhook/{plugin|theme|generic}/{slug}/`
- `/updatepulse-server-token/`
- `/updatepulse-server-nonce/`

An API class owns its rewrite rules, query variables, early request detection, authentication, authorization, dispatch, response status, and hooks. When adding or changing an API:

1. Add narrowly anchored rewrite rules during `init`.
2. Register every query variable used by the handler.
3. Implement `is_doing_api_request()` using the same public path so bootstrap classification remains correct before rewrite parsing.
4. Instantiate the API in the correct `upserv_run()` branch and include it in `upserv_is_api_request`; use `upserv_is_priority_api_request` only when the endpoint is safe with the minimal priority object graph.
5. Dispatch only explicit allowlisted actions. Never call an arbitrary method named by request input.
6. Keep public token/nonce authorization distinct from private API-key authorization and IP allowlisting.
7. Sanitize the response so file paths, credentials, crypto material, private metadata, and internal errors cannot leak.
8. Exit after a complete API response or file stream.
9. Set the rewrite-flush transient on activation or endpoint configuration changes; never flush on every request.
10. Document method, URL, headers, parameters, authentication, status codes, response bodies, side effects, and hooks.

Action dispatch should resemble an allowlist, not dynamic reflection:

```php
$actions = array(
	'browse' => array( $this, 'browse' ),
	'read'   => array( $this, 'read' ),
);
$action = isset( $payload['action'] ) ? sanitize_key( $payload['action'] ) : '';

if ( ! isset( $actions[ $action ] ) ) {
	wp_send_json( array( 'code' => 'action_not_found', 'message' => __( 'Unknown action.', 'updatepulse-server' ) ), 400 );
}
```

Update, Package, License, Webhook, and Nonce APIs have different authentication and response contracts. Do not normalize them casually. Maintain compatibility with the published examples in `docs/` and with existing hook timing (`pre_*`, operation filter, `did_*`, webhook scheduling) when modifying an operation.

## VCS support

VCS support crosses the settings UI, stored configuration, package metadata, webhook parsing, scheduler, update server, bundled Package Update Checker fork, icons, JavaScript, and documentation. A provider is not complete when its API class merely downloads an archive.

The current provider key-to-class contract is like:

```text
github    -> GitHubApi
gitlab    -> GitLabApi
bitbucket -> BitbucketApi
gitea     -> GiteaApi
...
```

`upserv_get_vcs_name( $type, 'edit' )` supplies the case-sensitive class stem. `Update_Server` constructs `Anyape\PackageUpdateChecker\Vcs\{Stem}Api`. Each saved configuration is keyed by:

```php
$vcs_key = hash( 'sha256', trailingslashit( $url ) . '|' . $branch );
```

Package metadata associates a package with that configuration through `origin => vcs`, `vcs`, `branch`, and `vcs_key`. Do not change this identity formula or metadata shape without a migration and backward-compatibility layer.

To add a provider, update all of these surfaces:

1. Add the provider key and display/edit name to `upserv_get_vcs_name()`.
2. Add `lib/package-update-checker/Vcs/{Stem}Api.php`, extending `Api` or the closest compatible provider and implementing authentication, connectivity testing, branch/tag/release selection, remote-file reads, commit time, archive URL construction, error reporting, and authorization headers as required.
3. Preserve the Package Update Checker strategies: release, tag, then configured branch unless `PUC_FORCE_BRANCH` forces branch behavior.
4. Add an explicit provider allowlist to remote-source validation. Never accept a class stem solely because a submitted `type` string exists.
5. Update the remote-sources template with labels, credential guidance, self-hosted controls where applicable, and a provider icon.
6. Update `js/admin/remote-sources.js` host recognition and service rendering. Self-hosted detection must retain the selected provider instead of guessing from an unknown host.
7. Update `Packages_Table::get_vcs_class()` and any details rendering.
8. Verify `Remote_Sources_Manager::vcs_test()` can instantiate the class safely and handles `WP_Error`, authentication failure, account/organization failure, and missing privileges without a fatal error.
9. Update webhook signature validation and payload URL/branch extraction for events that include a branch, omit a branch, or can match multiple saved configurations.
10. Preserve scheduled polling, manual registration, update checks, downloads, release assets, tags, forced branch mode, public/private authentication, credential failures, and self-hosted base URLs/ports where supported. List any affected runtime paths in the handoff as unverified when no test environment is available.
11. Update `README.md`, `readme.txt`, contextual Help content, the relevant `docs/*.md`, changelog/upgrade notice if applicable, and the POT catalog.

A provider test method must not assume a valid class or make an unguarded static call from user-controlled input. Resolve only allowlisted providers and return a structured error:

```php
$providers = array(
	'forge' => 'Anyape\PackageUpdateChecker\Vcs\ForgeApi',
);
$type = sanitize_key( $data['upserv_vcs_type'] );

if ( ! isset( $providers[ $type ] ) || ! is_callable( array( $providers[ $type ], 'test' ) ) ) {
	wp_send_json_error( new WP_Error( 'upserv_invalid_vcs_type', __( 'Unsupported VCS provider.', 'updatepulse-server' ) ), 400 );
}
```

Do not put provider-specific branches throughout `Update_Server`. Encapsulate provider HTTP and reference behavior in its VCS API class. Use filters only for genuine extension points, not to avoid completing the built-in provider integration.

## Public functions, hooks, and compatibility

Public procedural functions in `functions.php` are compatibility APIs. They should validate basic inputs and delegate to the class that owns the behavior. New public functions must be `upserv_`-prefixed, guarded, documented, and added to the appropriate developer document.

Actions describe events or execution points, for example `upserv_before_*`, `upserv_pre_*`, `upserv_did_*`, `upserv_*_ready`, and `upserv_scheduler_init`. Filters describe the value being filtered, such as `upserv_*_config`, `upserv_*_result`, or `upserv_submitted_*_config`.

For every new or changed public hook:

- Use the `upserv_` prefix.
- Pass enough context to avoid requiring globals.
- Preserve argument order and types once released.
- Add an inline docblock immediately before `do_action()` or `apply_filters()` with parameter types, meanings, return type for filters, and `@since`.
- Register callbacks with an explicit priority and accepted-argument count.
- Document the hook in the correct `docs/*.md` catalog and table of contents.

Prefer an existing public hook over duplicating core logic. Do not remove, rename, reorder arguments, narrow accepted types, or change response shapes without a deprecation path and documented migration.

## Coding standards

PHP must follow WordPress Coding Standards with the `WordPress-Extra` ruleset, as stated in `readme.txt`, plus these plugin conventions:

- Runtime baseline is PHP 8.0 or newer; activation enforces it. Do not use features newer than PHP 8.0 unless the declared minimum is intentionally raised everywhere and documented.
- Use tabs for PHP indentation and spaces for alignment only where WPCS permits.
- Use `snake_case` functions, methods, variables, and hooks; `Upper_Snake_Case` class names; uppercase plugin constants; lowercase kebab-case class files.
- Use strict comparisons and Yoda conditions where required by WPCS.
- Use WordPress APIs for HTTP, filesystem, options, cache, cron, localization, and responses unless the existing subsystem requires a lower-level primitive.
- Use fully qualified, namespaced classes. Import dependencies with `use` statements; remove unused imports.
- Add direct-access guards to executable PHP files.
- Do not suppress errors. If a legacy low-level operation must remain suppressed, keep the scope minimal, handle failure explicitly, and justify the targeted PHPCS ignore.
- Add a narrow `// phpcs:ignore Rule.Name -- reason` only when the rule genuinely cannot apply. Never silence a file or broad category to avoid fixing code.
- Avoid globals. If integration with WordPress requires one, use an `upserv_`-prefixed name and document it.
- Never log API keys, VCS credentials, cloud secrets, license crypto keys, tokens/nonces, signatures, personal data, full private payloads, or uploaded package contents.

All user-facing PHP strings use the `updatepulse-server` text domain. Add translator comments immediately before strings with placeholders. Escape at output, not prematurely during storage. Keep machine identifiers and stored enum values untranslated.

JavaScript should use the existing jQuery-ready/event pattern unless a feature deliberately introduces an isolated dependency. Use strict equality, terminate statements, avoid accidental globals, and keep translated strings in the localized object. CSS must remain scoped and responsive and must not override unrelated WordPress admin UI.

Do not mix cleanup/refactoring with a focused bug fix unless it is required for safety or correctness. When touching legacy code, improve the changed path without silently changing its public contract.

## Security requirements

Treat API, webhook, package upload/download, VCS, cloud-storage, license, and nonce code as security-sensitive.

- Check capabilities on admin pages, form handlers, and AJAX actions.
- Verify nonces on state changes; use the API's signature/token scheme for external callers rather than WordPress admin nonces.
- Authorize the requested operation after authentication. API key access lists, package ownership/whitelisting, license state, allowed domains, and IP allowlists are separate gates.
- Sanitize according to type, then validate business constraints. An endpoint allowlist is not authorization.
- Use `wp_safe_remote_*` when appropriate and guard against SSRF for stored or submitted endpoints. If self-hosted VCS/cloud endpoints require non-public hosts, document and narrowly control the exception.
- Validate archive names, package slugs, MIME/extension, size, hashes, extraction paths, and the resulting package structure. Prevent traversal and ZIP-slip.
- Use `WP_Filesystem` or established package-manager helpers and write only inside validated plugin data directories or configured cloud storage.
- Use prepared SQL for values and explicit allowlists for identifiers.
- Sign and compare secrets using the established cryptographic helpers and timing-safe comparisons. Do not invent a second token scheme.
- Return generic client errors and log only non-sensitive diagnostic context when debug logging is explicitly enabled.

For a public API operation, document the HTTP method, exact path, headers, body/query fields, field types, required/optional status, authentication flow, capability/access scope, success response, every material error status/body, side effects, and a safe example. For a public function or hook, document its signature, timing, arguments, return semantics, side effects, and a short executable example.

Keep documentation examples aligned with the real code and use placeholders for secrets. Never place a working credential, token, license, private endpoint, or personal data in documentation. Update manually maintained tables of contents and anchor links when headings change.

Release-affecting changes require an entry in the `readme.txt` changelog. Add an Upgrade Notice when users must rotate credentials, re-register packages, run a migration, reschedule jobs, flush rewrites, or take another manual action. Do not bump versions or stable tags unless the task includes preparing a release.

## Validation and exit conditions

This workspace does not include a runnable WordPress test environment. Require only checks that can be performed against the source tree unless the user explicitly provides another environment.

Agents must perform these checks:

1. Run `php -l` on every changed PHP file.
2. Run PHPCS with `WordPress-Extra` on changed PHP files. The installed binary is typically `~/.composer/vendor/bin/phpcs`; if its ruleset is unavailable, report that instead of claiming success.
3. Regenerate every changed minified asset and compare it with its source. Perform parser/syntax checks with an available local JS/CSS tool when possible.
4. Inspect the complete diff with `git diff --check` and the appropriate diff command for untracked files.
5. Search changed code for temporary logging, debugging statements, secrets, unsafe dynamic dispatch, unescaped output, unprepared SQL, missing capability/nonce checks, and stale references.
6. Confirm autoload paths, class names, hook names, callback argument counts, option paths, endpoint paths, asset handles, template names, and source/minified filenames agree across all touched files.
7. Verify documentation, manually maintained tables of contents, POT entries, migrations, uninstall behavior, and backward compatibility where applicable.
8. Confirm that only intended files changed and that no generated runtime data entered the repository.

`tests.php` is opt-in performance instrumentation loaded through `UPSERV_ENABLE_TEST`; it is not an automated test suite and cannot prove feature correctness.

In the final handoff, state the exact checks run and their results. Explicitly identify affected runtime behavior that was not verified. Never claim that a screen, endpoint, schedule, VCS provider, cloud operation, migration, or uninstall flow works merely because source-level checks pass.

A code change is ready for handoff when the applicable checks above pass, the diff and documentation are complete, compatibility or migration concerns are addressed, and unverified runtime behavior is stated plainly.
